# AI Monitor 开发方案

版本：0.3。状态：用户已确认开发；网页版已实现，正在真实联调与阶段验收。日期：2026-10-13（Asia/Shanghai）。

已明确的用户要求：邮件通知；先本地运行和验收；多源采集包含无需 API 的网页搜索采集、TwitterAPI.io 和公开原始来源；自动检查统一为 30 分钟；页面采用亮色；网页版可用且验收后再开发 Agent Skills。需求和验收编号见 REQUIREMENTS.md，MCP 接口核对记录见 API-RESEARCH.md。

## 1. 首版范围

做一个面向 AI 编程博主的个人热点情报工具，包含两条工作流：

- **关键词监控**：输入关键词或自然语言目标，例如“Claude 新模型正式发布”；系统定期采集候选信息，判断是否真正符合目标、有足够证据且是新事件，符合条件后发送邮件。
- **范围热点发现**：输入范围，例如“AI 编程 / 编程 Agent / 开源大模型”；系统定期筛选新信息、合并同一事件、生成中文摘要与关注理由，在网页展示。

关键词监控和范围热点发现的自动检查统一每 30 分钟执行一次；提供“立即检查”，但仍遵守来源限速与任务互斥。实际发现时间受信息源更新、搜索索引和请求耗时影响。

个人工具首版包含监控规则的新增、编辑、暂停、恢复、删除；热点筛选和详情；通知历史；运行状态和失败原因；服务配置状态。先不增加多用户管理、复杂权限和社交平台登录采集。

## 2. 信息采集与真实性判断

```text
搜索网页采集       TwitterAPI.io       多个公开 RSS/发布源
      └─────────────────┼─────────────────┘
                        ↓
        统一候选记录、来源状态与增量检查点
                        ↓
        核对原文、发布者身份、域名和时间
                        ↓
        OpenRouter 分析相关性、真实性与新颖性
                        ↓
           合并事件 → 持久化 → 网页展示
                        ↓
          新增且核实的规则命中 → 邮件队列
```

采集层使用独立适配器，所有启用且相关的来源均参与一轮采集，不能因某一路已经命中就停止其他来源。同一查询与相同订阅源跨规则复用；单路失败不阻断其他来源。记录成功、空结果、未配置、受阻、限流、超时、部分覆盖等状态。

**网页搜索采集**：后端直接请求普通搜索网址，通过统一 HTTP 客户端获取 HTML，再用 Cheerio 提取自然搜索结果标题、链接和摘要，获取原文核验。Bing 作为首选；DuckDuckGo HTML/Lite 作为待验证备选。本次 MCP 取样中 Bing 返回可解析结果，DuckDuckGo 搜索页读取失败，不把它标为已可用。搜索引擎 AI 摘要不进入确认事实的证据集合。

搜索不需要 API Key，也不默认借用 OpenRouter 联网插件。先以 HTTP + HTML 解析实现，选择器独立维护；如开发时发现必须执行 JavaScript，再按实际需要评估受限浏览器采集，不预装重型浏览器。公共搜索页面没有稳定 API 契约，必须识别页面结构改变或验证码，不能误显示零热点。

同一搜索引擎并发 1，相邻请求初始至少间隔 5 秒并添加少量抖动；每个去重后的查询每轮最多 1 页，初始解析上限 10 条。同一查询 30 分钟内复用结果；手动刷新沿用冷却与限额。遵守站点公开的访问要求，遇到 403/验证码停止本轮该来源，遇到 429 按 Retry-After 退避，不循环重试。默认每轮搜索请求最多 10 次，可在配置中降低；这些是本项目的保守起点，不是站点保证允许的频率。

**X / TwitterAPI.io**：服务端使用 X-API-Key 认证，调用 `/twitter/tweet/advanced_search`，设置 `queryType=Latest`。增量窗口采用 `since_time` / `until_time` Unix 秒数，避免已经停止支持的精确日期时间写法。按 `has_next_page` 和 `next_cursor` 分页，推文 ID 始终保存为字符串。辅助接入 `/twitter/user/last_tweets`，可信账号优先保存稳定 userId；用户名只作展示和初次解析。具体请求、响应与分页边界见 API-RESEARCH.md。

X 默认并发 1、相邻请求至少间隔 2 秒；每个查询每轮初始最多 3 页，并设每日请求/结果数量上限。达到上限记录部分覆盖与续查状态，不能直接把时间水位推进到窗口结束。没有 Key 时明确显示未配置，不伪装成 X 无结果。首版不申请实时流套餐。

**公开原始来源**：初始接入 OpenAI News RSS 与 Google AI Blog RSS，本次 MCP 均返回 XML；其他官方博客、Atom 发布记录和用户添加的订阅源按需扩展。开发阶段仍需验证本地进程出站访问、XML 解析及条目时间。缓存已见 GUID/链接；支持 ETag/Last-Modified，避免重复拉取未变化内容。

无论采集还是核验，HTTP 客户端统一处理超时、响应大小上限、重定向、出站代理和公共地址校验。网页内容和提取链接按不可信数据处理，避免原文抓取访问本地或私网服务。

AI 不凭自身记忆确认新闻。搜索原始页面、X API 返回的推文与发布者信息、公开源条目以及获取到的原文组成候选证据集合；模型引用只能指向服务端已取得的证据编号。最终域名、内容、时间和相关性均需核对，仿冒域名不能凭名称相似获得官方身份。抓取内容按数据处理，不能执行其中指令。

官方 X 账号身份依据官网关联及经过核验的稳定用户 ID，不凭蓝标、显示名称或互动数量确认。转载相同公告的搜索结果、RSS 和推文不算独立原始证据。文章或推文的更新时间与事件发生时间分别保存；只有抓取时间而无发布时间依据时，不能宣称发生了新的正式发布。

判断输出使用结构化字段：标题、中文摘要、是否命中规则、事件标识、实体与版本、时间依据、可信状态、证据编号、判定理由、选题价值及标签。OpenRouter 请求使用 `response_format.type=json_schema`，严格 Schema 和 `provider.require_parameters=true`；先确认所选模型及供应商端点支持。返回结果必须再通过服务端 Schema、证据引用和业务规则校验。不支持结构化输出时显示配置错误，不能静默改用自由文本后直接通知。

可信状态分为：

- **已核实**：有内容明确支持结论的官方原始来源，或可交叉印证的独立可靠来源，并通过相关性与时间检查。
- **待核实**：证据不完整、来源无法读取、信息只有传闻或来源冲突；网页允许查看，不发送正式发布通知，并在后续检查中重新核实。
- **已排除**：仿冒、旧闻重发、预测、与目标无关，或证据不支持标题结论；保留判定理由供排查。

这些状态是基于所获证据的判断，不承诺 AI 能百分之百识别假消息。发布类规则采用保守通知门槛；可在网页检查原始链接及判定依据。

热点排序综合领域相关性、时效性、独立来源数量、可获得的讨论信号与 AI 给出的选题价值。界面称为“关注度”，展示理由，不伪造访问量或讨论数；没有讨论数据时明确显示未获取。

## 3. 去重、定时运行与邮件

- 首次检查展示近期内容并建立基线，默认不批量发送历史邮件；后续新增且核实的事件触发通知。
- 同一事件的不同转载合并；规则与事件组成通知唯一键。正常监控期内发现的待核实事件升级为已核实时可触发通知；历史基线事件不因升级而批量发送旧闻。失败结果不能提前标记为已发送。
- API 与后台 worker 分开运行，共用 SQLite；网页关闭不会停止 worker。电脑休眠或服务退出期间不能监控；恢复后重新读取持久化规则并补查近期信息。
- 任务按持久化到期时间统一每 30 分钟调度，有并发上限和租约，避免手动执行、定时执行或进程重启造成重叠。每个来源独立保存检查点；失败来源不更新成功水位，恢复后从上次完成窗口补查，使用有限重叠窗口吸收延迟索引并以唯一 ID 去重。
- 分页只在本窗口完整获取并保存后提交时间水位；预算耗尽时保存窗口、游标和部分覆盖状态，后续继续补查。续查游标失效时重新查询原窗口并按 ID 去重，不静默跳过。AI 分析失败的候选内容持久化为待处理，不能因采集水位已经推进而被遗忘。
- 邮件通过 SMTP 发送，支持常见邮箱的服务器地址、TLS、账号和授权码。提供连接检查、测试邮件、发送记录和有限退避重试。
- 邮件包含事件标题、中文摘要、命中规则、核实依据、原始链接和发现时间。只有 SMTP 接受后记录“已提交”；是否进入收件箱由真实收件测试验收。
- SMTP 网络中断或崩溃后的重试可能涉及送达状态不确定；尽量通过持久化队列与固定 Message-ID 减少重复，不承诺端到端恰好送达一次。

## 4. 轻量技术方案

已按以下组合实现，安装版本固定在 package.json 与 package-lock.json：

| 部分 | 方案 | 目的 |
| --- | --- | --- |
| 前端 | React + 当前兼容的 Vite React TS 模板 | 响应式交互，开发与构建简单 |
| 服务端 | Node.js 24.16.0 + Express 5 + TypeScript | 按本机已验证运行版本实现 |
| 存储 | SQLite，封装 Node 24 的 DatabaseSync | 单文件持久化，不另装数据库服务 |
| 网页采集 | 统一 HTTP 客户端 + Cheerio | 直接采集搜索网页与原文，不需搜索 API Key |
| X 采集 | TwitterAPI.io REST API | 最新排序、增量时间窗口、分页与账号时间线 |
| 订阅采集 | RSS/Atom XML 解析 | 从多个公开原始发布来源获取内容 |
| AI | 服务端调用 OpenRouter HTTP API | 仅基于已取得证据分类、核验、摘要和排序 |
| 邮件 | Nodemailer SMTP | 兼容常见邮箱服务 |
| 调度 | 独立常驻 worker + 数据库任务记录 | 不依赖浏览器或外部定时平台 |
| 验证 | 核心逻辑/API 自动测试 + 浏览器验收 | 聚焦误报、漏报、去重和实际交互 |

已通过 MCP 获取 Node 24.16.0 专属文档，并检查本机接口。该版本 SQLite 稳定性标记为 1.2（Release candidate），使用 DatabaseSync；不照搬其他版本的 Database/Statement 方法。存储独立封装并锁定运行版本，方便以后更换驱动。短事务配合 WAL/busy timeout，事务中不等待网络请求。

本次 Context7 已核对 Vite 当前 React TypeScript 模板、Express 5 路由和错误处理、Cheerio HTML 解析、OpenRouter 结构化输出、Nodemailer SMTP。确认后按实际安装版本复核，保存 lockfile；不将资料取样版本当作已安装版本。Express 5 的页面回退路由采用有名称的通配符语法，API 404 先独立处理，避免被前端页面吞掉。

同一仓库包含前端、API、worker 和共享类型。一条开发启动命令运行所需进程；生产构建由 API 提供静态页面。本地默认仅监听回环地址，后续部署再处理公网访问方式。

主要数据：监控规则、信息来源、X 账号、来源检查点、候选文章/推文、证据、合并事件、规则命中记录、运行记录、邮件队列、非敏感设置及调用用量。候选记录统一包含 sourceType、sourceId、原始链接、最终链接、发布者、发布时间、采集时间、内容摘要指纹和可用互动数据。

OpenRouter Key、TwitterAPI.io Key 和 SMTP 授权码由服务端本地环境配置读取；示例配置不含真实密钥，浏览器接口和日志不返回密钥。设置页显示配置是否完整、模型选择、接收邮箱、30 分钟周期、来源启用状态和调用限制。出站代理在 HTTP 客户端按实际 Node 版本配置并验证，不能把 Vite 开发代理误认为服务端出站代理。

首版分别对网页采集、TwitterAPI.io 和 OpenRouter 设置请求/结果数量上限；AI 另记录 token 用量。只有服务返回实际费用时显示金额，不能将估算值标成真实消费。TwitterAPI.io 需要自己的 Key 与可用额度，无需 API 的约束仅针对网页搜索采集。相同内容复用分析结果，控制每轮候选数、并发和抓取大小。

## 5. 界面方向：FirstCue / 热点情报台

采用明亮的浅灰白底色、白色内容面板与墨绿文字，呈现一张清晰的“信号工作台”。首页围绕最新事件和来源证据展开；标志性区域是来源路径图，用真实采集渠道与事件的关联表现多源汇聚，不用随机数据装饰。

- 色彩：浅灰白 `#F6F8F3`、面板白 `#FFFFFF`、墨绿文字 `#163F3A`、青绿强调 `#147D71`、浅草绿 `#DCECBA`、琥珀强调 `#E8A33E`。正文和小标签使用足够深的文字色；浅草绿/琥珀只用于底色与图形，不能作低对比度正文。
- 字体：标题采用窄体展示风格；中文正文采用系统中文无衬线；时间、规则编号和状态采用等宽字体。优先本地与系统字体，避免界面依赖外部字体网络。
- 桌面：浅色功能导航、中间“最新信号 / 我的监控 / 通知记录”、右侧证据详情；首页明确展示最近/下次检查时间及网页搜索、X、订阅源的健康状态。
- 手机：单列内容与精简导航，证据详情进入抽屉；主要按钮易于触摸，不能只依赖悬停。
- 标志性交互：选中热点时，来源路径与证据详情联动，能看到它从哪几个渠道被发现、最终由哪些原始证据支持。没有实际数据时展示添加规则与配置来源的引导。
- 完整状态：加载中、没有结果、待配置、部分来源失败、AI 限额用尽、邮件重试均有明确说明和下一步动作。

布局为本产品单独设计；不采用通用企业门户模板。检查键盘焦点、文字对比度、手机触摸区域和减少动效偏好。

## 6. 实施顺序与人工确认点

1. **确认需求与方案**：已完成；用户明确回复“确认，开始开发”。
2. **开发网页与数据管理**：完成响应式界面、规则管理、持久化和配置引导；运行构建与基础交互检查，给用户可打开的本地预览。
3. **接入多源采集与 OpenRouter**：先按 MCP 资料和实际安装版本复核接口，完成搜索网页解析、TwitterAPI.io、多个公开原始来源、核验、结构化分析、事件合并和用量限制；用户在本地配置 OpenRouter 与 TwitterAPI.io Key，验证本地进程的真实联网链路。
4. **接入 worker 与邮件**：完成统一 30 分钟周期、增量检查点、重启恢复、邮件队列和重试，跑完整链路。用户在本地配置 SMTP 服务信息和接收邮箱，执行真实收件测试。
5. **网页版验收**：提供启动地址、测试报告和验收清单，用户实际验证新增监控、查看热点、证据判断、收邮件与关闭网页后的监控。修复发现的问题，等待网页版验收确认。
6. **开发 Agent Skills**：网页版通过后，再封装 SKILL.md 与 CLI/API 使用脚本，让其他 AI 添加规则、检查一次、查询热点和查看运行状态；复用同一套采集、核验与去重逻辑，并测试技能调用。

人工确认集中在方案确认、真实服务配置、网页版验收及最终技能验收，其余常规实现与修复连续推进。

## 7. 网页版验收用例

| 场景 | 通过标准 |
| --- | --- |
| 管理监控 | 新增、修改、暂停、恢复、删除生效，重启后仍保留 |
| 多源采集 | 搜索网页、X API 和至少两个域名的公开订阅源均有真实联调记录；单路故障时其他来源继续 |
| 搜索页面解析 | 只抽取自然搜索结果；验证码、结构变更、403/429 和真正零结果可区分；手动检查不能绕过冷却 |
| X 增量分页 | Latest 排序、Unix 秒数、字符串 ID、游标续查、空页和部分覆盖处理正确；账号蓝标不自动升级为官方 |
| 正式发布命中 | 有充分原始证据的新事件展示依据，并进入邮件队列 |
| 假消息与传闻 | 仿冒域名、预测内容及证据冲突不产生正式发布通知 |
| 旧闻与去重 | 历史基线和多篇转载不重复通知；不同新版本不会被误合并 |
| 待核实升级 | 后续获得有效证据时能升级并按规则通知 |
| 热点发现 | 配置范围可定时/手动执行，展示真实结果和排序理由 |
| 定时与重启 | 两类任务统一 30 分钟；浏览器关闭后 worker 继续；重启恢复任务；同时触发不重叠 |
| 外部服务失败 | 网页受阻、X API 错误、AI 返回非法 JSON、超时、限流、余额不足、SMTP 失败都有记录，不误显示成功 |
| 邮件 | 模拟 SMTP 验证格式与重试；实际 SMTP 验证用户收到邮件 |
| 响应式与交互 | 采用亮色；检查 375/768/1440px，表单、筛选、详情和键盘导航可用 |
| 真实链路 | 用用户配置完成搜索网页、X API、多个订阅源、OpenRouter 分析和实际收件测试；模拟测试不能替代此项 |

真实新闻结果具有时效性；业务边界使用可重复的固定测试证据验证，联网冒烟测试独立记录时间、来源和结果。
